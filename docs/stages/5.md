## Option 2 - the full destroy - and why it stayed out of scope



The spec asks for a **destroy / rebuild / replay** acceptance run, timed and
documented: tear the stack down, bring it back from Terraform, replay the
stream, and confirm the reconciliation still closes.

It is blocked by something specific rather than by effort.

**`infra/terraform/account/` is shared.** The account module holds the budgets,
the Cost and Usage Report, and the `plant-platform` Athena workgroup with its
per-query scan cap — and all three cover **WearWatch as well**, which is live
and which the operator has explicitly asked not to tear down.

So a full destroy would remove the cost guardrails from a running project in
order to time a rebuild here. That trade is not close.

Two honest options when the moment comes:

1. **Destroy only `infra/terraform/app/`.** The lake, Glue tables and app-level
   resources rebuild; the shared account foundation stays up. This is most of
   the acceptance value and carries none of the risk, and it is the version to
   do first.
2. **Destroy both**, once WearWatch's own teardown happens. That exercises the
   OIDC role and CUR path too, which option 1 does not, and it is the only
   version that proves the account can be rebuilt from nothing.

The CUR is worth flagging before anyone picks option 2: **it has no backfill.**
Destroying and recreating it does not lose the historical report data already
in S3, but it does create a gap for the period it is absent, and that gap is
permanent.

## What the acceptance run would actually prove

Not that Terraform works — `terraform apply` from zero was Phase 0 and is
already evidenced.

It would prove that the *reconciliation* survives a rebuild: same seed, same
generator, same manifest, a lake built from nothing, and 523 of 523 windows
still exact. That is a claim about determinism end to end rather than about
infrastructure, and it is the one worth timing.
