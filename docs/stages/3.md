# Phase 3 — dbt lakehouse

*Completed 2026-08-19.*

Glue tables, a silver layer that conforms two schema versions and flags late
arrivals, and a gold star with real SCD2 rows.

## The layers, and what each is allowed to be

**Bronze is raw as landed.** It contains the 92 duplicate copies the injector
published on purpose, and it should — removing them here would destroy the
evidence that reconciliation depends on. A bronze layer that quietly cleans is a
bronze layer you cannot audit.

**Silver conforms and dedupes.** `row_number()` over `event_id` ordered by
`publish_time`, keeping the earliest copy. `select distinct` was the obvious
alternative and is wrong twice: it would collapse rows differing only in
`publish_time` into an arbitrary survivor, and it would give no way to *count*
what was removed. Keeping the earliest publish also keeps `publish_lag_s`
honest, since that is the copy that actually arrived first.

**Gold is the star.** `dim_machine`, `fct_cycles`, `fct_defects`, and
`agg_window_machine`.

## Conforming the schema cutover

The v1→v2 drift renamed `operator` to `operator_badge` on cycle events. Staging
handles it with a `coalesce` across both names:

```sql
coalesce(
    json_extract_scalar(payload, '$.operator'),
    json_extract_scalar(payload, '$.operator_badge')
) as operator_badge
```

The added field (`line_id`) is the tolerable half of the drift — a reader that
ignores unknown keys survives it. **The rename is the half that actually tests
the layer**, because a reader assuming the old name produces nulls rather than
an error, and nulls flow all the way to a wrong aggregate without ever raising
anything.

## Windows in event time

The 15-minute window is computed in **event time, skew included**, because the
manifest records what the machine reported. See `docs/stages/1.md` — correcting
the skew first would be defensible engineering and would fail the grading for
the generator's own fiction.

## The second engine

*Added 2026-09-01.*

**The Athena target used to be the only target**, which meant dbt could not run
in CI at all — no credentials on a runner — and the entire warehouse layer went
unexercised on every push. A model set nobody can execute is a model set nobody
can check, which is an awkward position for a project whose thesis is that its
numbers are checkable.

`transform/profiles.yml` now also defines a **DuckDB** target reading the same
parquet objects the consumer wrote. Not a mock and not a fixture: a
disagreement between the two engines would be a real disagreement about the
data.

It required exactly two shims, both found by running it rather than by reading
docs:

| Athena | DuckDB | why |
|---|---|---|
| `json_extract_scalar` | `json_extract_string` | DuckDB has no `json_extract_scalar` at all, and `json_extract` returns the value **with quotes**, so a cast silently yields nulls |
| `from_unixtime` / `to_unixtime` | `to_timestamp` / `epoch` | neither Athena name exists in DuckDB |

A third was written and then deleted: `date_diff('second', a, b)` is accepted
verbatim by both, and a shim that wraps nothing is a private dialect with no
justification.

**Result: 32/32 models and data tests pass on DuckDB, and the ledger reports
523 of 523 windows reconciled** — the same answer Athena gave, from a different
engine over the same objects. Both now run in CI on every push, and a `broken`
window fails the build.

## What is still not done

**The Athena target is still not exercised in CI.** It needs credentials, and
claiming a dual-engine gate while only one engine runs would be the badge that
means nothing. DuckDB is what runs; Athena is what shipped.

A true parity gate — the same queries on both engines, compared scalar by
scalar — is the obvious next step. WearWatch runs exactly that across three
engines and it caught a real staleness bug on its first execution.
