# Phase 6 — Contract testing

*Completed 2026-09-01. Option 3 of the three offered.*

## Why this one

The spec offers a scale chapter, stream-side aggregation, or contract testing,
and says pick **one**.

Contract testing wins on a property the other two do not have: **this project
already produces the conditions it needs.** The generator performs a schema
cutover halfway through every run — `operator` becomes `operator_badge` on cycle
events, and `line_id` appears — so there is a stream that genuinely changes
shape while it is being consumed. A contract chapter written against a stream
that never drifts is a chapter about a hypothetical.

The scale chapter was the tempting one and is the wrong pick here. Running dbt
patterns against ~1B rows of NYC TLC data via Athena would cost real money to
learn something the Non-Goals already say this project is not claiming, and the
spec is explicit that a distributed engine may only enter if a chapter
*measures* a need. Nothing here has measured one.

## What a registry is for

Not documentation. A document cannot fail a build.

It exists to answer one question mechanically, before a change ships: *would
this break a consumer that is already running?* Three JSON Schemas in
`contracts/` are the input; `factorystream.contracts.compare` is the answer.

```
v1 -> v2: NONE
  added_field    payload.line_id            optional
  added_field    payload.operator_badge     required in the new version  [breaks backward]
  removed_field  payload.operator           required in the old version  [breaks forward]

v2 -> v3: NONE
  added_field    payload.duration_ms        required in the new version  [breaks backward]
  removed_field  payload.duration_s         required in the old version  [breaks forward]
```

**A rename is not a distinct rule.** It is a removal plus an addition, and it
breaks both directions — which is precisely why renames hurt and why the v1→v2
cutover is the half of the drift that actually tests silver. The checker
derives that rather than being told it.

The compatibility directions are worth naming carefully, because they are easy
to state backwards:

- **BACKWARD** — a consumer on the *new* schema can read *old* data. This is
  what matters when the producer moves first.
- **FORWARD** — a consumer on the *old* schema can read *new* data. This is
  what matters when consumers cannot all be upgraded at once, which in practice
  is always.

## v3, and why it is a unit change

v3 replaces `duration_s` (seconds, float) with `duration_ms` (milliseconds,
integer). That is a deliberately awkward choice, and it is the point of the
chapter.

The registry catches it: a removed required field and an added required one,
reported as breaking in both directions. Good.

Now consider the change it **cannot** catch — keeping the name `duration_s` and
changing only the unit to milliseconds. Every schema check passes. Every type
check passes. Every row validates. The numbers are wrong by a factor of a
thousand, every cycle-time aggregate downstream is wrong with them, and nothing
in the toolchain can say so, because **JSON Schema describes shape and a unit
is meaning.**

`tests/test_contracts.py::test_a_unit_change_that_keeps_the_name_passes_every_check`
asserts exactly that. It is a test whose *passing* is the bad news, written down
so the limit cannot be forgotten by someone reading a green suite.

`registry.SEMANTIC_CHANGES` lists three of these by hand — the unit change, a
redefined enum meaning, and a timezone convention change — because there is no
mechanism that could derive them. A registry that quietly implies full coverage
is worse than none: it converts an unknown risk into a believed-absent one.

## The gate

`contract_check` runs at the **producer**, before anything reaches the topic.

```
contract: 4,243 events checked (v1: 2,138, v2: 2,105)
          4 corrupt records skipped, by design
          all valid against their declared version
```

Three details that are decisions rather than defaults:

**Each event is checked against the version it declares.** Validating
everything against v1 would report the generator working correctly as a failure
— the fastest way to get a check switched off.

**Corrupt records are skipped, not failed.** They are unparseable by
construction, emitted on purpose at a declared rate. Counting them as contract
violations would make the gate fire on the disorder injector doing its job.

**A violation refuses to publish** (exit 2). A bad record reaching the topic
becomes somebody else's quarantine investigation; the cost of catching it here
is one exit code.

The numbers also cross-check the reconciliation from an independent direction:
4,243 parseable + 4 corrupt = 4,247 lines, and 4,151 deduped + 92 injected
duplicates = 4,243. Two different tools, counting different things, agreeing.

## v3 through the warehouse — and the bug it found

*Completed 2026-09-01, once the DuckDB target made the SQL runnable.*

This section previously said v3 did not flow through the warehouse, because
`profiles.yml` defined only an Athena target and there was no way to *execute*
the conforming SQL. Shipping a `coalesce` with a comment asserting it worked
would have been a claim about unexecuted code.

With a second engine, it could be run — and running it found something.

**Conforming v3 is a division, not just a coalesce**, because the rename
carries a unit change:

```sql
coalesce(
    cast(json_string('payload', 'duration_s') as double),
    cast(json_string('payload', 'duration_ms') as double) / 1000.0
) as duration_s
```

**Then the ledger reported 129 of 523 windows broken, with `event_delta`
exactly 0.** Counts reconciled perfectly; only durations disagreed, and the
warehouse observed *more* than ground truth expected.

The warehouse was right. **`manifest.py` was wrong** — it summed
`payload["duration_s"]` unconditionally, so under v3 that key does not exist
and ground truth silently recorded **zero** for every v3 cycle. The thing
grading the pipeline had itself gone stale against the contract.

Nothing raised. No count was wrong. A version-blind reader in the one component
that is supposed to be the reference, found only by running a third schema
version end to end.

Fixed with `events.cycle_duration_seconds`, one function that knows how a
duration is spelled in each version, used by the manifest writer and mirrored
by staging. `tests/test_contracts_end_to_end.py` builds its own lake with the
v3 cutover on and asserts four things: that v3 events were actually produced,
that all three versions reach silver, that v3 durations land in **seconds**
(a missing division shows up as a ratio near 1000), and that the ledger still
reconciles.

**v3 is off in the published scenario**, deliberately. Turning it on changes the
stream, the manifest, and every number in the dated reconciliation evidence.
Moving cited figures to demonstrate a feature would be the least honest thing in
the repository, so the test builds its own run and the documented one stays
reproducible.

One more thing worth noting: the project's own `accepted_values` test on
`schema_version` failed the first time a v3 row reached silver. That is exactly
what such a list is for — an undeclared schema version appearing in the
warehouse — and it was widened deliberately rather than pre-emptively.

## Running it

```bash
make contracts        # the compatibility matrix, and what it cannot see
make contract-check   # validate out/events.jsonl against declared versions
make build-duckdb     # the whole model set, locally, no AWS needed
pytest tests/test_contracts_end_to_end.py   # v3 through the warehouse
```

All of these run in CI on every push, and a `broken` window fails the build.
