# Phase 2 — Broker and consumer

*Completed 2026-08-19. Evidence: [`evidence/2026-08-19-phase2-broker.md`](../../evidence/2026-08-19-phase2-broker.md).*

The deliverable, verbatim from the spec: *"kill the consumer mid-batch, restart,
prove no loss and no duplicates in bronze."* Done against a live broker, and
running on every push since CI was added.

## The commit contract

```
poll → write to storage → COMMIT
```

Not the other order, and not auto-commit. With auto-commit the client commits on
a timer *before* the durable write, so a crash in between loses those records
silently, with no error anywhere. Committing after the write means a crash
leaves offsets uncommitted, the records are re-delivered, and idempotent object
naming absorbs the repeat.

```
consumed   4,247
  bronze   4,243 rows
  quarantine   4 rows
  objects      5
  commits      4
```

| Property | Test | Result |
|---|---|---|
| Committed work is not redone | re-run, same group | **0 consumed** |
| Replay does not duplicate | fresh group, offset 0 | 4,247 re-consumed → still 5 objects, 4,243 rows |
| A crash loses nothing | `kill()` mid-batch, restart | **0 events lost** |
| A crash duplicates nothing | same | row count matches published exactly |
| A crash changes nothing | clean vs crashed run | **identical bronze** |

`kill()` rather than a signal, deliberately: a graceful shutdown would flush and
commit, which is the behaviour the test exists *not* to exercise.

## Partitioning, and why two partitions are empty

```
factory.events — 6 partitions, replicas 1, keyed by machine_id

PARTITION  HIGH-WATERMARK
0          0
1          372
2          0
3          2042
4          1326
5          507
```

Eight machines hash across six partitions, so some take several and some take
none. That is correct rather than a bug. Keying buys **per-machine ordering
within a partition and nothing more** — which is exactly what Kafka guarantees,
and exactly why the out-of-order injector has to exist to test the rest.

The topic is created with 6 partitions explicitly. Auto-creation would give one,
and a single partition would silently satisfy every ordering assumption in the
project by removing the concurrency that makes ordering hard.

## Two bugs only the integration tests could catch

Both would have passed every unit test in the suite.

**The consumer could exit before it was ever assigned a partition.**
`--stop-after-idle` counted empty polls from the very first poll — but joining a
consumer group takes several seconds, and every poll during that window returns
`None`. A bounded run therefore hit the idle threshold *before receiving an
assignment*, consumed zero records, and exited reporting success. Silently
processing nothing while claiming to have finished is the worst available
failure mode. Idle now counts only once partitions are held.

**The test measured the generator, not the consumer.** The first version
asserted bronze contained zero duplicate `event_id`s, and failed with exactly
92 — precisely the number of duplicate copies the injector publishes on purpose.
Bronze is *raw as landed*, so those belong there and removing them is silver's
job. The assertion is now that bronze holds exactly as many rows as were
published: the consumer must add no duplication of its own.

That second bug is the more instructive one. The test was not wrong about the
code; it was wrong about *which component it was testing*, and it took a real
run to notice.
